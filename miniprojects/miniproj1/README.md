### CART 351 Mini-Project 1: Jack's Terminal
For the first mini-project, I originally wanted to create a site that would collect user data and use it to tell and shape the visuals of an ASCII narrative. However, during the ideation of this project, I discovered that it would be a much better demonstration of flask's capabilities to make something a little bit better suited to data storing and collecting, such as a terminal or user interface. I decided to try and recreate a command prompt terminal that would be used to store and save user data and notes, with the capacity to store different kinds of data and managing it different ways by just simply adding a command into the program. 
The biggest challenge with creating this project was dealing with unknown flask concepts, such as how to properly import and manage .json files simultaneously across a Javascript script and a python backend. I did a lot of research and hit a lot of roadblocks in efforts to make these two scripts communicate using the .json files I was organizing my database with. Additionally, I ran into a couple of issues with scope creep, where some commands took so long to figure out that I had to plan other ways around commands I wanted to make but wouldn't have time for. Breaking up the project into separate commands was very helpful as I could take it a step at a time, testing after each new implemented command and/or function and debugging as I went. 
I relate this project closer to Mimi Onuoha's ["The Point of Collection"](https://anomalse.github.io/CART351-Fall-2026/projects/files/The%20Point%20of%20Collection.%20The%20conceptual,%20practical,%20and%20ethical%E2%80%A6%20_%20by%20Mimi%20Onuoha%20_%20Data%20%20Society_%20Points%20_%20Medium.pdf), because of the nature of the program as a user interface. The program saved and safeguarded user data, that would only increase in volume and diversity as the project progressed and as more features were added. It made me think a lot about platforms with login systems and protections that supposedly safeguard user data. I added a command to my terminal called "user delete", that required a user to be signed out of any account they were into to delete. This may have seemed to most like it was accounting for an edge case in which a user deleted an account they were currently signed into, but no. I could just have easily signed them out before deleting them. The reason I added the user delete command was to give users a perspective into how transparent and unsafe their data might actually be. Of course, users would never know that their data was unsafe unless confronted with the user delete function, which then puts them in the power. Onuoha describes data collection as a "invisible transaction", where the invisibility of that deal comes in making one party the collector while the users are the collected. If we treat those that take and "keep" our data as equals, Onuoha puts emphasis on the power dynamic that arises from that relationship. So what if the user was the collector and collected, simultaneously at the mercy of their own data? That is the concept I was seeking to explore with this project
